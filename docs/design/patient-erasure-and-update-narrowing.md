# Narrowing front desk's update rights, and the two-person erasure of a patient's identity (review M1; pre-approved 2026-11-05, built as migrations 0032 and 0035)

**The problem, in plain words.** Front desk's database permission let one statement overwrite a patient's encrypted name, date of birth and phone, change the key-version numbers, or set the erased flag, move an identity token to another patient, or rewrite a duplicate-review row, with no audit row. No route did this; the permission was just too wide, and it contradicted the rule that erasure is never an incidental application path.

**What changed (0032).**
- Patients: the application role can no longer UPDATE the three encrypted fields, their key versions or `erased_at`. Key rotation runs as the migrator (unchanged; the rotation tests now run on the owner connection). A row lock (`SELECT ... FOR UPDATE`, used by the merge engine) needs UPDATE on at least one column, so a new counter column `lock_version` (nothing reads it) holds the only remaining UPDATE permission.
- Identity tokens: no UPDATE at all. Match candidates: UPDATE only on `status`, `resolved_at`, `resolved_by` (0029 already makes the pair immutable).
- **Erasure is a TWO-PERSON act (BUILD-SPEC 12.5: "processing an erasure request")**, kept in a ledger `mpi.erasure_requests` that the application role can only READ. Three SECURITY DEFINER functions (pinned search_path) write it, each checking the caller inside and writing its audit row in the same transaction:
  - `mpi.request_patient_erasure(patient, reason, key)`: front desk of the clinic; the patient is not erased and has no open request (one open request per patient).
  - `mpi.approve_patient_erasure(request, key)`: a DIFFERENT front-desk person of the clinic (the requester is refused); a patient in a live merge link is refused; then the encrypted name, date of birth and phone and their key versions are cleared and `erased_at` is set in one statement.
  - `mpi.cancel_patient_erasure(request)`: any front-desk person of the clinic, while the request is open.
  Every refusal that could reveal whether a patient or request exists is the same generic error. A replay of an approval or a cancel is a no-op returning false. The ledger rows are never deleted and move from requested to erased or cancelled exactly once (a trigger, enforced even for the owner).
- Routes: `POST /v1/staff/patients/{id}/erasure-requests`, `GET /v1/staff/erasure-requests`, `POST /v1/staff/erasure-requests/{id}/approve` and `/cancel` (step-up and an idempotency key on every write). The allowed reasons are a REQUIRED setting with no default, `CAREFLOW_ERASE_REASONS` (comma separated closed words): which reasons a clinic may erase for is a privacy and legal decision, so while it is unset the request route answers 503.

**0035 (reviewer finding).** Audit keys beginning `sys:` are reserved for the database's own functions: the application role's INSERT policy on `audit.log` refuses them, so a caller cannot plant a predictable key to suppress or break a definer function's audit row. The definer functions of 0032 and 0034 use server-made `sys:` keys.

**Residuals, named.** Messages are not erased by this path (their erasure and the retention periods are the purge design, `retention-and-erasure-purge.md`, which waits for the privacy owner). Identity tokens are kept: they are keyed hashes, and matching ignores an erased record. The two people are two front-desk accounts; a person who holds two accounts is out of scope (as for merges). The owner (migrator) can still change anything; that is accepted for the migrator.

**Tests.** Role matrix cases for all four routes (stepped and not, every role, the same-person refusal, merge-link conflict, reason list, replay) plus a matrix test that a completed erasure clears the columns and leaves exactly the request and erase audit rows; `tests/test_erasure_live.py` against the real database (including the reserved key prefix and that the application role can neither write the ledger nor update the identity columns); updated live tests that asserted the old column grants (`test_patient_binding_live`, `test_rls_mpi_scheduling_live`, `test_rls_mpi_worker_live`, `test_rotation_live`).
