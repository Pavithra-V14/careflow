## 0011_msg_threads_messages  (staff-only, encrypted body, erasure guard) + crypto.py + message rotation table
====================================================================
Prerequisite in the same file, before the FKs: `alter table mpi.patients add unique (id, clinic_id, origin)`.

### msg.threads
clinic_id, patient_id, topic ('care'|'appointments'|'safety'; 'readiness' is added by a later migration), status ('open'|'closed' default 'open'; not updatable, so closing is future work; documented), created_by uuid NOT NULL references iam.accounts, origin, created_at, idempotency_key.
FK (patient_id, clinic_id, origin) -> mpi.patients(id, clinic_id, origin). UNIQUE (patient_id, topic) [comment: one thread per patient and topic; may be relaxed later by a new migration]. UNIQUE (id, clinic_id, origin, topic).
Column-level INSERT grant: (clinic_id, patient_id, topic, created_by, origin, idempotency_key). id/created_at/status are server-set (client cannot backdate).
BEFORE INSERT trigger, caller-run: `select ... from mpi.patients where id = new.patient_id for share` (blocks a concurrent erasure) and refuses an erased patient (as mpi.check_merge_links does in 0008).

### msg.messages  (append-only; the body is ciphertext; no sender_account_id)
id (client-supplied uuid because the ciphertext's authenticated data binds it), clinic_id, origin, topic (denormalised), thread_id; FK (thread_id, clinic_id, origin, topic) -> msg.threads(id, clinic_id, origin, topic).
sender_kind ('patient'|'staff'|'system'), recorded_by uuid NOT NULL references iam.accounts (policy forces = auth.uid()).
  sender_kind='patient' means a message RELAYED by staff on the patient's behalf (a call, walk-in, forwarded note); recorded_by shows who typed it. In 0011 only 'staff' can be inserted (policy); 'patient' is enabled by 0012, together with the screening requirement.
body_ct bytea, body_key_version smallint, erased_at timestamptz.
  CHECK (erased_at is null and body_ct is not null and body_key_version > 0) or (erased_at is not null and body_ct is null and body_key_version is null).
  CHECK octet_length(body_ct) <= 40100 (technical guard for a 10,000-character cap enforced BEFORE encryption; not policy).
created_at, idempotency_key. UNIQUE (id, clinic_id, origin, topic).
BEFORE INSERT trigger, caller-run: lock the patient row FOR SHARE (through the thread) and refuse a message in the thread of an erased patient.
Privileges: SELECT; column-level INSERT (id, clinic_id, origin, topic, thread_id, sender_kind, recorded_by, body_ct, body_key_version, idempotency_key). NO UPDATE, NO DELETE, NO TRUNCATE for the app role.
Append-only trigger on UPDATE/DELETE/TRUNCATE for EVERY role including the owner, two permitted transitions, neither reachable by the app role (it has no UPDATE privilege): (1) erasure: body_ct and body_key_version set to null and erased_at set, nothing else changes, only when OLD.erased_at is null; (2) key rotation: only body_ct and body_key_version change, body_key_version MUST change, only when OLD.erased_at is null (an erasure is never reversible).
Erasure is a migrator-run procedure: it writes an audit.log row (ids only) for every erased message, and the runbook adds an invariant query "erased patient with a non-erased message" (alert metric tracked in the deferred list).

### msg.message_rotation_batches (new; 0010 is not touched)
clinic_id, origin, from_version, to_version (check <> from_version), messages_rotated integer > 0, first_message_id, last_message_id, created_at, idempotency_key (derived: 'rotate-messages:v{from}->v{to}:{clinic}:{origin}:{first}:{last}'). ENABLE+FORCE RLS with NO policy and NO grant to the app role: written only by the migrator-run rotation. Documented: message rotation needs the migrator credential because the app role cannot update messages.

### RLS (all FORCE; patients, guardians, admin, business_owner, auditor and other clinics get NOTHING on msg; topic allowlists so a future topic is default-deny to front desk)
| table | SELECT | INSERT |
|---|---|---|
| threads | nurse, doctor (any topic); front_desk only topic in ('appointments','safety') | nurse, doctor (any topic) or front_desk only topic='appointments'; created_by = auth.uid() |
| messages | same as threads, on the row's own topic | same roles/topics as threads; recorded_by = auth.uid(); sender_kind = 'staff' only |
Every policy is row-local (topic is on the row): no helper function, no join, no recursion. INSERT...RETURNING works for front_desk because its INSERT topic is a subset of its SELECT topics.

### Code shipped with 0011
* careflow/crypto.py: new field `message_body`; for it only, a PER-MESSAGE subkey derived by HKDF-SHA256 from the version's master key with info = 'careflow/message_body/v1/' + message uuid (so each key encrypts exactly one message: the random-nonce volume concern in crypto.py:25-26 does not apply to messages, and a ciphertext cannot be moved to another row). The existing name/dob/phone ciphertext format is unchanged (regression test). The vault gets `encrypt_message_body(plaintext, message_id, key_version)` / `decrypt_message_body(...)`.
* careflow/messages.py (new): builds an encrypted message row (length cap before encryption); the ONLY module besides crypto.py and rotation.py that may call decrypt_message_body (AST test). Plaintext is never logged, never in an exception, never returned. There is no read route in this scope; a staff read route is future work and gets its own role-matrix case in the same change.
* careflow/rotation.py: rotate/verify/version_usage extended to message bodies (batches written to msg.message_rotation_batches); a key cannot be retired while any message body uses it.

## 0012_msg_screenings  (record_screening, worst-of view, review-task changes)
====================================================================
Prerequisite in the same file: `alter table agents.review_tasks add unique (id, clinic_id, origin)`.
Also here (because they depend on screenings): the messages INSERT policy is replaced to allow sender_kind in ('staff','patient'), and the deferred constraint below is created.

### msg.screenings  (written ONLY by msg.record_screening)
id, clinic_id, origin, topic, message_id; FK (message_id, clinic_id, origin, topic) -> msg.messages(id, clinic_id, origin, topic).
outcome ('red_flag'|'clear'|'unassessable'), profile ('demo'|'clinical'), rules_evaluated integer >= 0, rule_set_hash text NOT NULL,
review_task_id uuid; FK (review_task_id, clinic_id, origin) -> agents.review_tasks(id, clinic_id, origin),
patient_reply ('not_required'|'pending_clinician_template'), screened_by uuid NOT NULL references iam.accounts (set from auth.uid() by the function), created_at, idempotency_key.
CHECKs: review_task_id NOT NULL for 'red_flag' and 'unassessable' and NULL for 'clear' (extends "required for red_flag, forbidden otherwise" to unassessable, because decision 3 requires a linked nurse task); outcome='clear' => profile='clinical' and rules_evaluated > 0; outcome='red_flag' <=> patient_reply='pending_clinician_template'.
UNIQUE (message_id, profile).
Table trigger (caller-run, applies to every writer): the linked task must have kind 'red_flag' (for red_flag) or 'screening_unassessable' (for unassessable), assigned_role = 'nurse', status = 'open' (at link time), and source_message_id = message_id::text.
Masking: the function and the trigger both take `pg_advisory_xact_lock(hashtextextended(message_id::text, 0))` first, then refuse any non-red_flag row for a message that already has a red_flag row in ANY profile (a red_flag may be added after a clear: a later look can only escalate). The READ side does not rely on the trigger: see the view.
Column comments (verbatim): patient_reply: `# CLINICAL-PLACEHOLDER: needs clinician sign-off` (the emergency reply to the patient is NOT sent, no wording is stored or written anywhere; a later migration adds 'sent' once a clinician-approved template exists); the unassessable task priority: `# CLINICAL-PLACEHOLDER: needs clinician sign-off` "priority 'standard' pending clinical lead confirmation"; table: screening rows are never training labels (CLAUDE.md rule 9); the screening is NOT bound to the text that was screened (residual risk above).
Privileges: app role SELECT only. No INSERT/UPDATE/DELETE privilege.

### kb.active_red_flag_rules(p_clinic uuid, p_origin text, p_profile text)  (definer helper, pinned search_path, not granted to the app role)
Mirrors careflow/rules.py select_active_versions exactly (newest version first; a retired version withdraws the rule; the first version whose status the profile may use is in force; clinical = approved only, demo = approved + draft_unreviewed). Returns the rules in force. rule_count = those with phrases or patterns; rule_set_hash = sha256 over the sorted 'rule_id:version_id' lines. A parity test runs the Python selector and this function over the same fixture rows.

### msg.record_screening(p_message_id uuid, p_outcome text, p_profile text, p_rules_evaluated int, p_rule_set_hash text, p_match_provenance jsonb, p_idempotency_key text) returns uuid
LANGUAGE plpgsql SECURITY DEFINER, `set search_path = ''`; `revoke all ... from public, anon, authenticated, service_role`; `grant execute ... to careflow_app` only.
Order of work:
1. Load the message (as definer; relies on the migrator owner having BYPASSRLS exactly as has_clinic_role does in 0001; a live test proves it). Check the CALLER with iam.has_clinic_role: nurse, doctor, queue_worker of that clinic, or front_desk only when the message topic is appointments or safety. A missing message, another clinic's message, a wrong role and a wrong topic ALL raise the same 42501 with the same text (no existence oracle).
2. Take the per-message advisory lock.
3. Replay: look up by (message_id, profile) only; the same idempotency key and ALL the same parameters returns the existing id; anything else raises the same generic conflict error.
4. Recompute rule_count and rule_set_hash from kb.active_red_flag_rules for the message's clinic, origin and the claimed profile; the caller's p_rules_evaluated and p_rule_set_hash must equal them. 'clear' is refused when the in-force set has no rule with criteria (H2).
5. For red_flag and unassessable the FUNCTION raises the review task itself (M3: front desk no longer inserts these kinds directly): kind 'red_flag' (priority 'immediate') or 'screening_unassessable' (priority 'standard'), assigned_role = 'nurse', source_message_id = message_id::text, idempotency key derived from the screening key. Provenance = validated p_match_provenance (allowlisted keys and scalar types only: rule_id, rule_code, version_id, rule_status, kind, index, start, end, profile, outcome; string length capped; so patient text cannot be stuffed in), plus for unassessable the keys "placeholder": "# CLINICAL-PLACEHOLDER: needs clinician sign-off" and "priority_note": "pending clinical lead confirmation".
6. Insert the screening (screened_by = auth.uid()) and an audit.log row (action 'msg.screening.recorded', resource ids only, no text), idempotency key derived from the screening key.

### Deferred constraint trigger (initially deferred)
On msg.messages for rows with sender_kind='patient': a screening row for the message must exist by commit. The checking function is SECURITY DEFINER, search_path '', read-only EXISTS (it must not depend on the committing role's SELECT rights). `SET CONSTRAINTS ... IMMEDIATE` can only make it fail earlier; a rolled-back savepoint is judged on the final state. Stated residual risk (M9): a staff member can mislabel a relayed patient message as sender_kind 'staff' and no screening is then required. Mitigations: the view below lists every message with no screening regardless of label (a watchdog metric is tracked in the deferred list), and process/training. It is NOT closed by the database.
Note: a demo-profile `unassessable` row satisfies the constraint and still raised a nurse task (safe, stated).

### msg.message_screening_status  (view, security_invoker = true, so the caller's RLS applies)
One row per message: effective_outcome = worst of ALL screening rows (red_flag > unassessable > clear), or 'unscreened' when there is none. Readers must use this, never "latest" or "the clinical row".

### review-task RLS changes (M1, M3), replacing 0007's select/insert policies on agents.review_tasks (fix-forward)
* SELECT: nurse, doctor, admin, queue_worker, any kind (unchanged; admin keeps escalation visibility); front_desk ONLY kind in ('unmerge_review') (allowlist of today's non-message kinds, so every future kind is default-deny to front desk).
* INSERT: nurse, doctor, admin, queue_worker, any kind (unchanged); front_desk ONLY kind = 'unmerge_review' (identity.py's unmerge). Front desk raises red_flag / screening_unassessable tasks only through msg.record_screening.
* careflow/rules.py: RedFlagEngine.escalate_red_flag keeps working for nurse/doctor/admin/worker; the request-path call for a front-desk caller goes through record_screening instead. The affected existing tests in tests/test_rules_live.py (front desk raising tasks, around lines 436-440) are updated in the same change.

## 0013_patient_account_binding  (H1 version)
====================================================================
Defect: patients_insert_front_desk / patients_update_front_desk let ANY single front-desk user set mpi.patients.account_id on INSERT or UPDATE, binding any account to any record; the account then passes patients_select_own. The 17.2 claim check (verified contact AND date of birth match) is not enforced in the database. Nothing in application code sets account_id today.
* Column privileges: revoke INSERT and UPDATE on mpi.patients from careflow_app; re-grant INSERT on every column EXCEPT account_id, and UPDATE only on (name_ct, name_key_version, dob_ct, dob_key_version, phone_ct, phone_key_version, erased_at) (everything rotation and ingestion update today). ON CONFLICT DO UPDATE SET account_id therefore also fails for the app role.
* Trigger, every role including the owner (BEFORE INSERT OR UPDATE): an existing non-null account_id can never be changed or cleared. NULL -> value is allowed (so migrator seeding and the future claim function keep working) only if the target account is active, account_type in ('patient','guardian') and has the same origin as the patient; this check runs in a SECURITY DEFINER helper with pinned search_path (a caller-run read of iam.accounts would be hidden from front desk by RLS).
* Scope: 0013 only protects the binding. The claim FUNCTION that enforces the 17.2 rule in the database is deferred to the portal phase (tracked). Until it exists, nothing in the application role can bind an account.
* Existing code and tests: careflow/rotation.py:210-222 and careflow/mpi.py:261 are unaffected; tests/test_rls_mpi_scheduling_live.py seed_patients (migrator, active 'patient' accounts, origin 'test') is unaffected.

# v3.1 AMENDMENTS to msg-proposal-v3.md (same folder). These SUPERSEDE any conflicting text in v3. They answer the per-migration review of v3 (0011 BLOCKED 1 HIGH, 0012 BLOCKED 2 HIGH, 0013 SAFE with 4 MEDIUM). Design only; nothing in db/ exists.

## Amendments to 0011
* **[HIGH fix] Erased-patient guard.** The two caller-run FOR SHARE triggers are REPLACED by trigger functions that are themselves SECURITY DEFINER (search_path ''), owned by the migrator (BYPASSRLS, as has_clinic_role relies on), `revoke all ... from public, anon, authenticated, service_role, careflow_app` (trigger functions need no grant). They take (patient_id, clinic_id, origin) and first require `iam.has_clinic_role(clinic_id, array['front_desk','nurse','doctor'])`; otherwise they raise the SAME generic error an RLS failure gives (no existence or erasure oracle across clinics, because triggers fire before WITH CHECK). Then `select ... from mpi.patients where id = ... and clinic_id = ... and origin = ... for share`, and a missing or erased patient raises that same generic error. This works for nurse and doctor even though patients_update_front_desk is front-desk-only, because the lock is taken as the definer.
* **Erasure lock order (pinned in the migration comment and the runbook):** the erasure procedure FIRST updates mpi.patients.erased_at (this takes the row lock that conflicts with FOR SHARE), THEN erases the patient's message bodies in later statements of the same transaction under READ COMMITTED. The FK's implicit KEY SHARE does not conflict with a non-key UPDATE, which is why the explicit FOR SHARE exists. A held FOR SHARE blocks rotation of that patient's row until commit (accepted).
* **Rotation entry point.** Message rotation is a SEPARATE function rotate_message_bodies(conn, vault, ...) that requires the migrator connection: it REFUSES with a loud error (never a silent skip) when run as the app role. version_usage for messages is computed by the migrator, unscoped (an app-role count would be RLS-scoped and under-count); key retirement uses only that count.
* **Crypto details.** `message_body` is NOT added to FIELDS; the generic encrypt/decrypt reject that name. A separate method pair derives a message-specific ROOT with a distinct HKDF label first (HKDF-SHA256(master_v, info='careflow/message_body/root/v1')), then the per-message subkey (HKDF-SHA256(root, info='careflow/message_body/key/v1/' + message_uuid)); this removes cross-use of the demographic secret. AES-GCM AAD = 'careflow/message_body/v1/' + clinic_id + thread_id + message_id (distinct from the demographic AAD prefix). Wording corrected: a subkey is unique per message ID (a retry with the same id and different plaintext reuses it; harmless). Line endings are normalised and blank text refused (as for the other fields).
* **Append-only trigger specification.** A row-level BEFORE UPDATE OR DELETE trigger AND a separate statement-level BEFORE TRUNCATE trigger. "Nothing else changes" is a comparison over EVERY column other than those a transition may touch. The trigger cannot verify that a rotated ciphertext decrypts to the same plaintext (that read-back is code in rotation) and cannot stop ALTER TABLE ...
