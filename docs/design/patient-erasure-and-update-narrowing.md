# Narrowing front desk's update rights, and an audited erasure path (review M1; pre-approved 2026-11-05, built as migration 0032)

**The problem, in plain words.** Front desk's database permission let one statement overwrite a patient's encrypted name, date of birth and phone, change the key-version numbers, or set the erased flag, move an identity token to another patient, or rewrite a duplicate-review row, with no audit row. No route did this; the permission was just too wide, and it contradicted the rule that erasure is never an incidental application path.

**What changed (0032).**
- Patients: the application role can no longer UPDATE the three encrypted fields, their key versions or `erased_at`. Key rotation runs as the migrator (unchanged). A row lock (`SELECT ... FOR UPDATE`, used by the merge engine) needs UPDATE on at least one column, so a new counter column `lock_version` (nothing reads it) holds the only remaining UPDATE permission.
- Identity tokens: no UPDATE at all. Match candidates: UPDATE only on `status`, `resolved_at`, `resolved_by` (0029 already makes the pair immutable).
- Erasure: `mpi.erase_patient(patient, reason, idempotency key)`, a SECURITY DEFINER function (pinned search_path) executable by the application role. It checks the caller is front desk of the patient's clinic now (active-role aware), refuses a patient in a live merge link, clears the encrypted fields and sets `erased_at` in one statement, and writes the `patient.erase` audit row (reason code, role scope) in the same transaction. A missing patient and a caller who may not erase get the SAME generic error. A replay is a no-op returning false.
- Route: `POST /v1/staff/patients/{id}/erase` (front desk, step-up, idempotency key). The allowed reasons are a REQUIRED setting with no default, `CAREFLOW_ERASE_REASONS` (comma separated closed words): which reasons a clinic may erase for is a privacy and legal decision, so while it is unset the route answers 503.

**Residuals, named.** Messages are not erased by this path (their erasure and the retention periods are the purge design, `retention-and-erasure-purge.md`, which waits for the privacy owner). Identity tokens are kept: they are keyed hashes, and matching ignores an erased record. The owner (migrator) can still change anything; that is accepted for the migrator. Recorded erased rows keep their ids and the audit trail.

**Tests.** Role matrix cases for the route (stepped and not, every role, merge-link conflict, reason list, replay) plus a live test that the columns are cleared and exactly one audit row exists; updated live tests that asserted the old column grants (`test_patient_binding_live`, `test_rls_mpi_scheduling_live`, `test_rls_mpi_worker_live`); `tests/test_erase_route.py` offline.
