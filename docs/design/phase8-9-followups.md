# Phase 8 and 9 follow-ups: voice and care-gap storage, canary cap, owner-delete recommendation (2026-11-06)

Owner decisions of 2026-11-06. No real voice engine; the fake stays. Migrations 0043, 0044 and 0045, each with a reviewer pass (findings applied before merge), a grants-ledger row, and role-matrix and live tests.

## 0043: a daily cap on canary documents (decision 4)
`docs.register_canary_document` now takes `p_max_per_day` (a required value; NULL, below 1 or above 1000 is refused) and refuses a NEW canary document once the clinic already has that many today (UTC). A replay of an existing key is still answered. The check is serialised per clinic by an advisory lock, and a primary-key collision gives the same fixed refusal instead of a raw error. The old uncapped function is dropped. The application setting `CAREFLOW_CANARY_MAX_PER_DAY` has the placeholder **20** in `config/demo-phase4.yaml` (labelled DEMO ONLY) and is unset elsewhere; with no cap the sweep injects nothing. Residual: the cap is supplied by the trusted worker, so it limits a runaway loop, not a malicious worker.

## 0044: care-gap tables and routes (decision 2)
`ops.care_recurrence_rules`, `care_episodes`, `care_episode_rules`, `care_barriers`, `care_review_samples`; forced RLS; nurse, doctor and admin of the clinic read; the application role may insert and resolve **barriers only** (column grants; resolve is final, with the database clock and `resolved_by = the caller`). Rules, episodes and samples are read-only for the application: their producers (clinician data entry, the sampler) are separate reviewed packages. Routes: `GET /v1/staff/care-gaps`, `POST .../barriers`, `POST .../barriers/{id}/resolve`, each with role-matrix cases and an audit row. The panel counts a rule with an unknown last-done date separately and never calls it overdue.
Open: who produces episodes, rules and samples; the worker has no read policy, so the overdue alert is *shown* (`flagged_overdue`) but not raised as an `ops.alerts` row by the tick; a barrier can be recorded for an erased patient (accepted, documented in the migration).
`CAREFLOW_CARE_GAP_ALERT_DAYS`: demo placeholder **14**, unset elsewhere (the panel then reports `alert_age_configured: false`).

## 0045: voice preference, sessions, transcript sink (decision 2)
`msg.voice_preferences` (the patient's own `voice_enabled`, off by default), `msg.voice_sessions` (consent time from the database; `transcript_retention_days` with **no default**), `msg.voice_transcript_chunks` (ciphertext only, a per-chunk key, expiry computed by the database from the session's retention, insert-only, no SELECT right, no delete before expiry). **The opt-in is enforced by the database**: a session cannot be inserted unless the account's own preference is on, the account is an active patient and it is bound to a patient of that clinic. Routes (patient accounts only, no staff multi-factor; `tests/test_mfa.py` pins the narrow exemption): `GET/PUT /v1/portal/voice/preference` and `POST /v1/portal/voice/sessions`, which answers 503 while the clinic flag, an engine or `CAREFLOW_VOICE_TRANSCRIPT_RETENTION_DAYS` is missing. With no engine wired it is always 503. The retention has a demo placeholder of **30** (the spec's starting value); unset elsewhere.
Open: reading transcripts (admin, audited, spec 9.4) and the purge of expired chunks are later packages with their own grants and review.

## Found while doing this
The acknowledge route for alerts called `auth.uid()` from application SQL; the restricted role cannot (spec 18.1), so the real route would have failed. Fixed to pass the id from the verified claims; a test now forbids `auth.uid()` in application SQL text. The alert sink and the new helpers also avoid `ON CONFLICT` (PostgreSQL then also checks the SELECT policy, which the writing role deliberately fails: CI run 42201883307).

## Owner-delete recommendation (decision 5), for counsel to confirm
- **No deletes from append-only ledgers by anyone, including the owner, except the audited erasure path** (`mpi.*_patient_erasure`) and, for transcript chunks, deletion of rows past their expiry by the audited retention purge. The triggers already refuse the application role; the recommendation is that the owner role is treated the same by procedure, and that any exception is a new migration with an audit row.
- **Restore drills restore from backup into a separate empty project**; they never repair a live ledger by deleting or editing rows. A restore must leave `session_replication_role` at its default so the append-only triggers keep firing (the drill checks that they do).
- For counsel to confirm: whether the erasure path plus expiry-based purge satisfies the statutory record-keeping duties, and the retention periods in spec 9.4.
