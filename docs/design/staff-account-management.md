# Staff invitation and role management (pre-approved 2026-11-05, built as migration 0034)

**Before.** Accounts and role grants were created by a script run by the owner; the application role could not write to `iam` at all, and a sign-in needs the Supabase Auth admin API (the secret key).

**What was built.**
- **Five SECURITY DEFINER functions** (pinned search_path), each doing exactly one thing, checking the caller INSIDE, writing its own audit row in the same transaction, and raising one generic error on any refusal: `iam.invite_staff_account`, `iam.grant_staff_role`, `iam.revoke_staff_role`, `iam.set_staff_account_status` (suspend and reinstate), `iam.activate_own_account`. The application role gets EXECUTE on them and still no INSERT or UPDATE on `iam.accounts` or `iam.staff_roles` (the migration verifies that).
- **Who:** invite, grant, revoke: an active admin of the clinic (under the active role). Suspend and reinstate: an admin of EVERY clinic where the target holds a live role, never oneself, only active <-> suspended. Activate: the invited person themselves, and only when their token shows a verified second factor (aal2); an admin cannot activate someone. `queue_worker` can never be granted this way (worker identities stay operator-created). A revoke that would leave a clinic with no active administrator is refused.
- **Routes** (`/v1/staff/accounts`): `GET` (list a clinic's staff accounts and live roles; admin), `POST /invite`, `POST /{id}/roles`, `POST /{id}/roles/revoke`, `POST /{id}/suspend`, `POST /{id}/reinstate` (admin, with step-up, idempotency key), `POST /activate-me` (the person's own act; needs a second factor in the token).
- **The sign-in** is created through an Auth admin PORT (`careflow/auth_admin.py`). With none configured the invite route answers 503. A fake is used in tests and the demo. The real adapter is written against Supabase's documented invite endpoint, is NOT verified by a real call, refuses to exist unless `CAREFLOW_AUTH_ADMIN_VERIFIED` is a past or present date and a secret key is set, and is NOT wired at start-up: the secret key stays out of the web process until the owner chooses to wire it. It has an entry in the data-flow register (not permitted in clinical).
- **No e-mail address is ever stored** in our tables, an audit row, a log line or a response; the audit details hold the role word and the role scope only.

**Reviewer pass 2026-11-05 applied:** replay is decided by state (never by reading `audit.log`, whose keys a caller could plant); audit keys are server-made with the reserved `sys:` prefix (0035); the last-administrator check is serialised per clinic with an advisory lock (also for suspensions); nobody grants a role to THEMSELVES; the functions are revoked from `anon`, `authenticated` and `service_role`.

**Residuals.** Granting `admin` is one admin's act (a two-person rule for admin grants is not built; the audit row names who). Suspending someone does not end their already-issued token before it expires (tokens are short-lived; the grant check is live on every request, so a suspended account loses access on its next request). Changing the e-mail or deleting the Auth user is not covered. If the database step fails after the sign-in was created, an unused Auth user remains (an operator can remove it); the invite is idempotent on the address.

Tests: `tests/test_staff_routes.py` (offline), `tests/test_staff_accounts_live.py` (the functions against the real database) and matrix cases for all seven routes.
