# Grants ledger

Every NEW database grant, policy widening or SECURITY DEFINER function added from 2026-11-05 on, in plain words, so the owner can review them later in one place. A line is added in the SAME commit as the migration that creates the grant. Tightenings (removals and narrowings) are listed too, marked as such. Format: migration, what, who gets it, why, how to undo.

| Migration | Kind | In plain words | Who | Why | Undo |
|---|---|---|---|---|---|
| 0031 | NEW TABLE + GRANT | A new table `sched.offer_deliveries`: a record that a person delivered an offer by hand. The application role gets SELECT and INSERT on it, nothing else; a trigger refuses UPDATE, DELETE and TRUNCATE for every role. | Front desk inserts (as themselves); front desk, nurse and doctor read | Phase 3 delivery with no external service | `drop table sched.offer_deliveries` in a new migration (nothing else depends on it) |
| 0032 | NEW TABLE + THREE FUNCTION GRANTS + TIGHTENINGS | (a) NEW TABLE `mpi.erasure_requests` (a ledger of two-person erasure requests): the application role can only READ it, and only front desk of the clinic. (b) NEW: the application role may EXECUTE three definer functions that request, approve and cancel an erasure; approval needs a DIFFERENT front-desk person than the requester and is what clears the patient's name, date of birth and phone. (c) NEW COLUMN `mpi.patients.lock_version` with UPDATE for the app role (a counter nothing reads, so row locks keep working). (d) REMOVED: the app role's UPDATE on a patient's encrypted fields, key versions and `erased_at`; all UPDATE on identity tokens. (e) NARROWED: UPDATE on match candidates to `status`, `resolved_at`, `resolved_by`. | Front desk of the clinic (the functions check inside) | Review finding M1 + BUILD-SPEC 12.5 | Drop the functions and table and restore the column grants in a new migration |
| 0033 | NEW FUNCTION GRANT | The application login may EXECUTE `sched.release_expired_holds()`, a definer function that expires old holds and reopens their slots, only for clinics where the caller is a queue worker. | Queue workers (the function checks inside; everyone else is refused) | Scheduled tidy-up of expired holds | Drop the function in a new migration |
| 0034 | FIVE NEW FUNCTION GRANTS | The application login may EXECUTE five definer functions that create and change staff accounts: invite a staff member, grant a role, revoke a role, suspend or reinstate an account, and let an invited person activate their own account (only with a second factor). Each checks inside that the caller is an admin of the clinic (or the person themselves) and writes the audit row. The application login still cannot write the account or role tables directly. | Admins of a clinic (the invited person for activation) | Staff invitation and role management | Drop the functions in a new migration |
| 0035 | TIGHTENING | The application role may no longer write an audit key beginning `sys:` (reserved for the database's own functions), so a planted key cannot suppress their audit rows. | Everyone but the database's functions | Reviewer finding on 0032/0034 | Replace the policy in a new migration |
| 0036 | NO GRANT CHANGE | A merge of a record into itself is left to the table's own check (the same refusal as before 0029); the candidate tie only applies to two different records. | Nobody | CI on main (identity link-rules test) | Replace the function in a new migration |
| 0037 | WIDENING (narrow) | Front desk of a clinic may write and read the saved state of the Scheduling runs (checkpoint rows whose thread id starts `scheduling:`) in its own clinic, and replace the special pending writes of those threads.
